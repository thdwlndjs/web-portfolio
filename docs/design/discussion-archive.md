# Web Portfolio Redesign — 논의 맥락 아카이브 (재구성본)

> **중요:** 이 파일은 이 대화에서 확인 가능한 메시지·결정을 순서대로 재구성한 **맥락 보존 문서**이며, 6,317줄의 원본 채팅 전문이 아니다. 원본 6,317줄은 현재 작업 환경에 실제 파일로 제공되지 않았다. 필요하면 사용자가 원문 내보내기를 별도 보관하고 이 문서를 색인으로 사용한다. 원문으로 인용·검증하지 말 것.
>
> 사용 방법: Codex는 `redesign-spec.md`를 먼저 읽고, 특정 선택의 이유나 기각된 대안을 확인할 때만 이 문서의 해당 절을 검색한다. **과거의 추천이나 AI 시안 문구는 현재 명세가 아니다.**

## 0. 작업의 배경과 목적

- 프로젝트: `web-portfolio`의 새로운 포트폴리오 UI. 본 대화에서 공개 미리보기 `https://thdwlndjs.github.io/web-portfolio/redesign-preview/#featured` 확인.
- 채용 포지셔닝: AI 응용 개발에 강점이 있는 **신입 소프트웨어 개발자**. AI 연구 전문가라고 과장하지 않고, 프로젝트로 실제 문제 해결과 구현을 보여주는 목표.
- 처음 사용자 요구: 이력서/대외활동/자격·수상·인턴십을 모두 담되, 채용 관점에서 중요한 정보와 프로젝트의 시각적 강조 균형을 잡기.
- 시각적 목표: AI 생성 템플릿 같은 조잡함(‘AI Slop’) 회피, 강한 첫인상, 과도한 장식 지양, 레퍼런스에 근거한 정교한 편집 디자인.
- 초기 임시 팔레트: Cloud Dancer 계열 `#F2F0EB`, ink `#20221F`, accent `#9D4337`. 사용자가 **색상은 다른 제안을 검토**한다고 했으므로 최종 확정 아님.
- 도구 역할: ChatGPT에서 레퍼런스 분석과 디자인 의사결정, Codex에서 원본 소스 분석과 프로토타입 구현, 기능 TDD, Playwright 기반 Visual QA.

## 1. 레퍼런스 복원과 좌우 분할 채택

1. 사용자는 과거 보았던 “반 나눠지고 깔끔한” 포트폴리오를 다시 찾아 달라고 요청했다.
2. Brittany Chiang `https://brittanychiang.com/`를 본 뒤 사용자가 **“네 맞고요”**라고 명시적으로 확인했다.
3. 사용자는 당시 전체 페이지 스크린샷을 제공했고(현재 작업 환경 파일명 `portfolio-fullpage(1).png`), 기존 화면은 대체로 왼쪽에 자기소개·이력 정보, 오른쪽에 대표 2개와 추가 카드 그리드가 있었다.
4. 초기 어시스턴트는 사용자의 질문을 “디자인 확정”으로 잘못 읽고 코덱스 구현 지시로 성급히 넘어갔다. 사용자 정정: **“아니 디자인 논의를 이제 시작해야함”**.
5. 따라서 실제 원본 레퍼런스를 보고 사용자가 판단한 뒤 결정하는 탐색 프로세스를 채택.
6. Brittany Chiang의 레이아웃에서 차용할 것은 좌우 분할, 타이포그래피, 여백, 탐색 흐름. 콘텐츠를 전부 오른쪽에 복제할 의무는 없으나 후속 대화에서 오른쪽 상세 이력도 수용하기로 함.

## 2. 왼쪽 패널의 역할: 여러 차례 정정 뒤 선택된 구성

### 2.1 초기 갈등
- 첫 분류 A(이력서 요약형), B(정체성 중심형), C(미니멀 소개형)에 대해 사용자 반응: **“셋이너무단순 AB사이의 뭔가인데”**.
- 사용자가 처음엔 수상·소개 등을 왼쪽에 몰고 오른쪽을 프로젝트 전용으로 구상했으나, Brittany 방식의 소개·탐색이 낫겠다고 판단.
- 채용 담당자 관점을 반영해 왼쪽을 단순 네비게이션이 아닌 ‘지원자 요약 패널’, 오른쪽을 ‘역량 검증’ 공간으로 제안.

### 2.2 구체적으로 마음에 든 시안
사용자가 아래 시안을 직접 인용하면서 **“이게 좋아 나는”**이라고 말했다.

```
[왼쪽 패널]
이름
Software Developer
AI 응용 시스템과 백엔드 개발에 관심을 두고, 실제 문제를 해결하는 서비스를 만듭니다.

PROFILE AT A GLANCE
기업 연구소 인턴십 3회
소프트웨어공학 전공 · 2027 졸업 예정
프로젝트 우수상 · 학술대회 발표

01 Projects
02 Experience
03 Education & Awards

GitHub · Email · Résumé
```

- 이 구조가 현재 기준. **프로필 라벨·간결한 설명과 3줄 이력 분리**, 탐색과 외부 링크는 하위 위계.
- 이후 세밀한 타이포 A/B/C 제안보다 위 시안을 선호한다고 명확히 했다.
- 이름/학력 문구는 실제 인적사항·소속 학과의 공식 명칭을 원본과 확인한 뒤 표시해야 함.
- 가로폭은 38:62 또는 35:65 등 여러 시작값을 검토; 수치 확정은 하지 않았다.

## 3. 대표 프로젝트 2개: 구조·카드·이미지의 구분

1. 오른쪽 대표 프로젝트는 **News Bias Explorer**와 **Smart Wardrobe Agent** 두 개.
2. 서로 나란한 2열 쇼케이스 vs 세로 1열 크게 보여주는 안에서 사용자는 **“대표 프로젝트 2개 세로형”**을 선택.
3. 개별 카드의 시각적 중심을 A 비주얼 우선 / B 균형 / C 기술성과 우선으로 비교.
4. 사용자 판단: **“골자는 B로 일단 가보자 A가 좋아보이는데 그거는 플젝 하나하나의 웹디자인이 개선되어야 할거같아”**. 따라서 **균형형**을 기본으로, UI 개선 이후 이미지 강조형 재검토 여지 보존.
5. 카드 외형 A(오픈) / B(명확한 컨테이너) / C(얇은 경계·여백 절충) 비교 후 사용자가 **C를 선택**.
6. 이미지 배치 레퍼런스 재조사 후 사용자: **“대표는 1먼저 실험”**. 여기서 1은 각 프로젝트 이미지와 설명을 한 행에서 좌우 분할하는 방식. 카드 두 개 자체는 여전히 세로로 쌓는다. 이미지 왼쪽·오른쪽 교차 여부는 명시적으로 확정되지 않았다.
7. 대표작 Hover: 강한 모션보다 배경·링크·화살표 등 절제된 반응을 우선 채택.
8. 구체 타이포/패딩 제안은 나왔지만 대부분 시험 범위이며 최종 승인된 토큰이 아니다.

## 4. 추가 프로젝트 9개: 카드 그리드에서 에디토리얼 목록으로

1. 기존 추가작은 2열 카드 그리드였음. 사용자에게 A 썸네일 목록 / B 에디토리얼 인덱스 / C 그리드 / D 텍스트 리스트 레퍼런스를 제시.
2. 사용자: **“추가 프로젝트는 A+B 결합형을 우선 실험하자.”** 작은 썸네일과 읽기 쉬운 목록의 장점을 결합하되, 대표작보다 정보가 압축되는 구조.
3. 전체 페이지 시안 1/2를 비교했고 사용자는 **시안 1(대표작 큰 비중, 추가작 세로 목록)**을 우선 실험하기로 함.
4. Hover 대안을 비교하여 **“대표 절제형, 추가 프로젝트는 확대 미리보기 실험”** 채택.
5. 미리보기 위치: 커서 팝업(A) / 일정 위치 고정(B) / 커서 추적(C) 중 **B 고정** 선택.
6. 고정 위치 B1 목록 옆 vs B2 목록 상단에서 **B1 목록 옆**을 택하는 방향.
7. AI가 생성한 시안에서 이미지 옆 미리보기 공간에 제목·설명·기술까지 넣었다. 사용자 반응: **“레퍼에서는 옆에 이미지만 떠야 깔끔한거같은데 그 위치에 설명도 같이 포함시키는데 왜 그런식이야?”**.
8. 따라서 **목록에는 프로젝트명·기능 요약, 옆에는 이미지만**이 확정된 강한 제약. 이미지 패널이 별도 프로젝트 상세 카드가 되면 안 된다.
9. 선택/전환: Hover/Focus에 해당 이미지를 표시; Crossfade 180~220ms는 실험값. 목록에 남길 메타정보의 정확한 표현은 실제 화면 검증 대상.
10. 데스크톱에서 이미지 패널을 고정할 범위는 **추가 프로젝트 섹션 안쪽**; 브라우저 뷰포트 전체에 무한히 따라다니게 만들지 않음.

## 5. 모바일 추가 프로젝트: 작은 이미지 → 탭하면 펼침

1. 초기 48/72/96px 작은 썸네일로 모바일 목록을 보여주는 안 비교.
2. 사용자 직접 반응: **“아예 안보이긴 하는데,,ㅋㅋ”** — 중요한 것은 내부 UI가 알아보이느냐인데 작은 썸네일은 그 역할을 못함.
3. 대안: 기본 상태는 제목+설명만 보이는 간결한 목록, 관심 있는 항목 탭하면 **큰 이미지가 그 행 아래에 펼쳐지는 구조**. 사용자: **“그래그래그게좋겠다”**.
4. 펼침 비율 16:9/4:3 중 사용자 **“4:3으로 먼저 실험해보자”**.
5. `object-fit: contain`으로 실제 화면을 자르지 않는다. 한 번에 하나 펼치기(다른 항목 누르면 이전 닫힘)는 우선안.
6. 첫 탭은 이미지 펼침이고, 프로젝트 이동은 별도 상세 링크로. 모바일 접근성과 인터랙션 충돌을 고려한 구조.
7. 아직 실제 프로젝트 캡처를 넣은 최종 모바일 화면 승인은 이루어지지 않았다.

## 6. 모바일 상단 정보·탐색

1. 모바일 소개 영역 M-A(이름·직무·소개·핵심 이력 3줄) vs M-B(핵심 이력 한 줄 압축) 비교.
2. 사용자: **“모바일 첫 화면은 M-A 소개와 핵심 이력 3줄 강조을 우선 실험하자”**. 결과적으로 스크롤이 길어질 위험보다 지원자 정보의 가시성 우선.
3. 모바일 탐색은 A 햄버거 vs B 인라인 메뉴 중 사용자 **B 소개 아래 인라인 메뉴** 선택.
4. 인라인 메뉴 외형 A 텍스트 링크 vs B 테두리 칩에서 사용자 **A 텍스트 메뉴** 선택.
5. 실제 모바일 화면에서는 줄바꿈, 터치 타깃, 대표작 시작 위치를 확인해야 함. 모바일도 데스크톱 고정 레이아웃을 억지로 유지하지 않음.

## 7. 타이포그래피: 산세리프 → SUIT

1. 실제 레퍼런스: Brittany Chiang(명료), Rauno(강한 크기 대비), Lee Robinson(세리프/에디토리얼).
2. 사용자 **“타이포그래피는 A 산세리프 통일”** 선택. 혼합 세리프는 현재 보류.
3. 후보 Pretendard, SUIT, Wanted Sans 비교. 사용자가 Pretendard와 SUIT를 실제 화면에서 비교하자고 함.
4. HTML 비교 프리뷰가 생성되었고 사용자가 **“일단 SUIT로 가자”**. 이로써 **SUIT Variable 우선 채택**.
5. 글자 크기/자간/행간은 가안을 제시한 상태이며 최종 시각 승인 전. 기술 라벨 등 한글·영문 혼용의 실제 줄바꿈 검증 필요.
6. 폰트 라이선스·로딩/네트워크·fallback 확인은 구현 품질 단계에서 다룬다.

## 8. 색상과 하단 이력 영역: 아직 결정하지 않음

- 초기에 Cloud Dancer 변형 `#F2F0EB`, 잉크 `#20221F`, 테라코타 `#9D4337`를 일관되게 사용했고 일부 대비 검토도 수행.
- 이후 사용자 명시: **“색상 다른제안받아볼게”**. 즉, 채택된 조합도 최종 확정 아님. 새 팔레트를 임의 추가하거나 기존 팔레트를 최종 확정해서는 안 됨.
- `Experience`, `Education & Awards`는 우측 콘텐츠 끝에서 탐색되어야 함. 그러나 이력 상세 섹션의 실제 레이아웃/하위 그룹/시각 표현은 **미확정**.
- 프로젝트 내용 외 이력 정보의 누락을 막아야 하지만, 상세 사실·날짜·수상명은 자료 대조가 필요함.

## 9. 로컬 프리뷰 확인 후 발견한 차이

공개 프리뷰: https://thdwlndjs.github.io/web-portfolio/redesign-preview/#featured

직전의 페이지 텍스트 조회에서 확인된 요소(이번 ZIP 제작 과정에서 새로 코드 실행/렌더 검증한 것은 아님):

- 왼쪽 헤드라인 `채용하세요. 끝까지 가는 신입 AX 개발자` — 사용자 승인 카피가 아니고, 직무 포지셔닝에 비해 강한 채용 요구 문구.
- 왼쪽 핵심 이력이 `1차 프로젝트 우수상`, `대학생 맞춤형 매칭 플랫폼 논문 발표`, `정보처리기사`로 구성 — 승인한 3줄(인턴십·학력·우수상/학술발표)과 불일치.
- 대표작은 News Bias Explorer와 Smart Wardrobe Agent가 표시되고 핵심 구현 항목이 존재.
- 추가작 9개 이름은 표시되나 일부 요약이 `핵심 보조 프로젝트`, `추가 프로젝트`라 프로젝트 기능 설명 역할이 약함.
- 미리보기 이미지 일부 존재, WantWear/CoachCU/Personalized Travel Curator/Knowledge Graph/RecycleCenter 등은 `실제 화면 캡처 준비 중` 상태가 확인됨.
- 추가 미리보기 영역에 이미지 외 설명이 남아 있을 수 있으므로 현재 구현을 실제로 조사해 규칙 위반 여부 확인 필요.
- `이력 · 기술`은 `UNDER REVIEW`라는 임시 섹션으로 남아 있음.
- Sticky/Hover/반응형 실제 모션·SUIT 렌더링은 페이지 텍스트만으로 확인되지 않았으므로 Codex Visual QA가 필요.

**이 목록은 Phase 1에서 다시 조사할 대상이지, 이번 문서 제작 시 검증 완료된 코드 감사 보고서가 아니다.**

## 10. 개발 프로세스 선택: Matt Pocock 방법론을 ‘대화 방식’으로 차용

1. 사용자는 Matt Pocock의 Grill Me / Grill with Docs / To Spec / TDD / Wayfinder 등을 채용할 가치가 있는지 물었다.
2. Codex에 스킬을 설치하면 실행할 수 있지만, 이 ChatGPT에서 **스킬을 설치하거나 실행하는 것은 아님**. ChatGPT에서 방법론을 따라 요구사항 탐색을 진행하는 것으로 결정.
3. 사용자가 “디자인의 모든 선택 전에 실제 레퍼런스”를 반복해서 요구함. 새로운 결정을 AI가 건너뛰지 않도록 프로토콜로 고정.
4. 디자인 탐색 중 일부 결정이 생기면 `Grill Me`형 질문을 하되, 단순한 양자택일 설문만 반복하지 말고 실제 시각적 대안으로 비교.
5. Codex에 넘길 시점에는 사용자/ChatGPT가 설계한 요구사항을 SDD 명세로 작성하고, **동작하는 기능**(nav, Hover/Focus, 아코디언, 링크 등)에 TDD 적용.
6. 색감·여백·시각적 완성도는 테스트 통과만으로 판단할 수 없으므로 Playwright 스크린샷·Visual QA와 사용자 승인을 구별.
7. Codex는 먼저 Phase 1 Audit & Specification을 수행하여 원본 코드/테스트 환경/미구현을 조사. 구현은 승인 이후.
8. 사용자 우려: 기존 6,317줄을 채팅에 통째로 넣을지 파일로 넣을지; MD 파일 자체가 품질을 높이지 않음. **현재 명세와 과거 맥락을 분리하고 필요한 부분만 선택 조회**하는 것이 기대 효과.
